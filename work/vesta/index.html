The product

Overview

I built Vesta to keep coding-agent work in one place. The desktop workspace shows activity and results while the CLI offers the same core workflows for people who prefer the terminal.

The problem

It can be hard to see what a coding agent is doing, how much a run has cost and whether it has actually stopped.

Why it mattered to me

I wanted one view where I could work with a model and still see the commands, edits and costs around it.

My role

  • Designed and implemented the desktop workspace and CLI.
  • Built model selection and routing, run activity, usage accounting and cancellation into the workflow.
  • Added browser tests for the interface and fixtures that demonstrate operation without calling live providers.

Architecture

Hard problems

Making Stop actually stop

Model calls are provider CLI subprocesses. The first version used a 20-minute blocking subprocess.run, so the Stop button did nothing and a late reply could overwrite the screen. I rebuilt the path end to end: a cancellation event threads from the JavaScript button, through the Qt bridge and pipeline, to a streaming Popen reader that checks it about five times a second and kills the whole process tree — including grandchildren that could otherwise keep spending money or editing the repo. Stale results are rejected by request ID.

Routing by capability, not by list order

Auto mode originally picked the first configured free model and stopped at the first error. I replaced it with capability-based selection: score the models the user actually has for the task, try the cheapest capable one, and fall back automatically on empty answers, rate limits or auth failures — asking for confirmation only when a call is genuinely paid, destructive or irreversible.

TestingMocked provider runtimes — no test ever spends moneyLive provider tests in CIFast, free and deterministic; live behaviour is covered separately by an opt-in provider canary.

Testing & reliability

I test run behaviour in Python and use browser fixtures to verify how activity, cancellation and costs appear in the workspace.

Lessons

  1. A run timeline is only helpful if completed, cancelled and failed work are reported consistently.
  2. Provider integrations are easier to evaluate when model selection, execution and accounting have clear boundaries.

Project status

The current build is a private alpha. The screenshots use its real interface with test fixtures. Costs in those screens are demonstration values.
